# 운영 BI 지표 정의집 (Ops Metric Definitions)

- 버전: v1.2 (2026-11-05)
- 근거: `docs/ops_bi/01_eda_kpi_candidates.md`, `sql/eda/08~09_*.sql`
- 원본: `bigquery-public-data.ga4_obfuscated_sample_ecommerce.events_*`

---

## 0. 운영 원칙

1. **이 문서가 유일한 기준이다.** 대시보드, CSV, AI 코멘트의 모든 숫자는 이 문서의 `metric_id` 정의로만 계산한다.
2. **SQL은 metric_id를 주석으로 남긴다.** 예: `-- metric: K01_revenue`. 문서와 SQL이 1:1로 추적되어야 한다.
3. **정의를 바꾸면 버전을 올리고 변경 이력(8장)에 남긴다.** 과거 리포트와 숫자가 달라지는 이유를 설명할 수 있어야 한다.
4. **집계 전에 대사(6장)를 먼저 통과해야 한다.** 대사가 실패한 날은 숫자를 내보내되 "해석 보류"로 표시한다.
5. 기존 분석 프로젝트의 `docs/metric_definitions.md`와 `core_f_orders`는 수정하지 않는다. 운영 BI는 이 문서와 `ops_*` 테이블을 쓴다.

## 1. 기본 단위와 키

| 단위 | 키 | 정의 |
|---|---|---|
| 사용자 | `user_pseudo_id` | GA4 익명 ID. 실제 회원 ID가 아니다. |
| 세션 | `session_id = user_pseudo_id + '-' + ga_session_id` | ga_session_id 누락 0건 (EDA 확인) |
| 세션-일 | `session_date × session_id` | **일별 집계의 실제 단위.** 자정을 넘긴 세션은 각 날짜에 1번씩 집계된다 |
| 주문 | `order_key` | 아래 1-1 규칙 |
| 날짜 | `event_date` | **UTC 기준.** 430만 건 모두 `event_date`가 UTC 날짜와 일치 (`sql/eda/10`) |
| 통화 | `ecommerce.purchase_revenue` | **USD.** 구매 5,692건 모두 currency=USD, `purchase_revenue_in_usd`와 100% 일치 (`sql/eda/10`) |
| 주 | 월요일 시작 (`WEEK(MONDAY)`) | 기존 분석 프로젝트와 동일 |

### 1-2. 집계 창 규칙

일별 테이블(`ops_kpi_daily`)에는 비율이 아니라 **분자와 분모를 따로** 저장하고, 7일·월 누적은 분자 합 / 분모 합으로 다시 계산한다. 일별 비율의 평균을 쓰지 않는다.

| 창 | 범위 (기준일 D) | 비고 |
|---|---|---|
| 당일 | D | |
| 전일 | D−1 | 표시만 하고 판정에 쓰지 않음 (요일 효과) |
| 같은 요일 | D−7 | |
| 최근 7일 | D−6 ~ D | |
| 직전 7일 | D−13 ~ D−7 | |
| 이번 달 누적 | D가 속한 달 1일 ~ D | |
| 지난달 같은 기간 | 지난달 1일 ~ 지난달 같은 날짜 (말일이 짧으면 말일까지) | |

- 창 안에 하루라도 빠진 날이 있으면 그 창의 값은 **비워둔다** (잘못된 비교보다 비교 없음이 낫다).
- 증감 표기: 건수·금액 지표는 증감률(%), 비율 지표는 차이(%p).
- 사용자 수는 날짜끼리 더하면 같은 사람이 중복된다. 그래서 7일·월 누적의 활성 사용자는 **사용자-일 합계**(DAU의 합)이며, 고유 사용자 수가 아니다.

### 1-1. 주문 키 규칙 (중복 제거)

GA4는 주문이 아니라 이벤트를 기록한다. 결제 완료 페이지를 새로고침하면 같은 주문의 purchase 이벤트가 다시 기록된다. 그래서 주문은 아래 키로 묶고 **가장 먼저 기록된 이벤트 1건만** 남긴다.

```text
order_key =
  transaction_id가 있으면       → 'T:' + transaction_id
  없거나 '(not set)'이면        → 'S:' + session_id + '|' + purchase_revenue
```

**근거 (검증 쿼리: `sql/eda/08_session_dedupe_validation.sql`)**

| 확인 | 결과 | 판단 |
|---|---|---|
| 중복 transaction_id 중 같은 세션 안에서 발생 | 326개 중 311개 (95%) | 중복은 세션 안 새로고침 패턴 → 세션이 거래번호 없는 건의 대체 키로 적합 |
| 한 세션에 서로 다른 transaction_id가 2개 이상 | 236개 세션 | "세션당 주문 1건"으로 세면 실제 주문을 놓침 → 세션 + 금액으로 구분 |
| 거래번호 없는 구매가 있는 세션 | 813개 | 이 중 같은 세션 안에 2건 이상은 38개뿐 |

**알려진 한계**
- 거래번호 없는 주문이 같은 세션에서 같은 금액으로 2번 실제 결제되면 1건으로 합쳐진다. (드문 경우로 판단)
- 같은 거래번호가 서로 다른 세션에 걸친 15건은 첫 세션에만 주문이 남는다. (6장 대사 R3에서 차이로 설명)

## 3. Tier 1 헤드라인 KPI (확정)

각 지표는 아래 항목을 모두 채워야 "확정"이다: 정의 · 계산식(분자/분모) · 단위 · 포함/제외 · 빈 값 처리 · 7일·월 누적의 의미 · 판정 기준 · 표기 · 알려진 한계 · SQL 위치.

| metric_id | 지표 | 계산식 | 판정 기준 (flag) |
|---|---|---|---|
| K01_revenue | 매출 | `SUM(IFNULL(purchase_revenue, 0))` | 최근 7일 vs 직전 7일, ±25% 초과 |
| K02_orders | 주문 수 | `COUNT(order_key)` | 최근 7일 vs 직전 7일, ±25% 초과 |
| K03_sessions | 세션 | `COUNT(*)` on 세션-일 | 같은 요일 대비, ±20% 초과 |
| K04_active_users | 활성 사용자 | `COUNT(DISTINCT user_pseudo_id)` | 같은 요일 대비, ±20% 초과 |
| K05_session_cvr | 세션 전환율 | 주문 세션-일 / 세션-일 | 최근 7일 vs 직전 7일, ±0.20%p 초과 |
| K06_aov | 객단가 | 매출 / 매출이 있는 주문 수 | 최근 7일 vs 직전 7일, ±15% 초과 |

### K01_revenue · 매출

- **정의:** 그날 발생한 주문(중복 제거 후)의 구매 금액 합계
- **계산:** `SUM(IFNULL(purchase_revenue, 0))` from `ops_f_orders` where `order_date = D`
- **단위:** USD
- **포함:** 중복 제거 후 남은 모든 주문. 날짜는 주문의 첫 purchase 이벤트 날짜
- **제외:** 같은 주문의 재전송 이벤트 (같은 날, 다른 날 모두)
- **빈 값:** 매출값이 없는 주문은 0으로 더한다. 그래서 매출 누락이 많은 날은 매출이 실제보다 낮게 나온다 → DQ03이 경고·보류
- **7일·월 누적:** 일별 매출의 합
- **표기:** `$12,340` (소수점 없음)
- **한계:** purchase 이벤트의 금액 그대로이며, 세금·배송비·환불 반영 여부는 GA4 구현에 따라 다르고 이 데이터로는 확인할 수 없다
- **SQL:** `03_ops_kpi_daily.sql` (`revenue`)

### K02_orders · 주문 수

- **정의:** 그날 발생한 고유 주문 수
- **계산:** `COUNT(*)` from `ops_f_orders` where `order_date = D` (1행 = 1 `order_key`)
- **포함:** 매출값이 없는 주문도 1건으로 센다 (거래 규모는 매출 누락과 무관하게 본다)
- **제외:** 재전송 이벤트
- **7일·월 누적:** 일별 주문 수의 합
- **표기:** `1,284`
- **한계:** 거래번호가 없는 주문은 세션+금액으로 묶으므로, 같은 세션에서 같은 금액으로 실제 2번 결제하면 1건이 된다
- **SQL:** `03_ops_kpi_daily.sql` (`orders`)

### K03_sessions · 세션

- **정의:** 그날 이벤트가 1건 이상 있는 세션 수
- **계산:** `COUNT(*)` from `ops_f_sessions` where `session_date = D`
- **포함:** 모든 이벤트 종류 (session_start가 없어도 그날 이벤트가 있으면 포함)
- **7일·월 누적:** 세션-일 합계. 자정을 넘긴 세션은 2번 세어진다
- **판정:** 주말이 평일보다 약 30% 낮아서, 전일이 아니라 같은 요일과 비교
- **표기:** `3,968`
- **SQL:** `03_ops_kpi_daily.sql` (`sessions`)

### K04_active_users · 활성 사용자

- **정의:** 그날 이벤트가 1건 이상 있는 고유 사용자 수 (DAU)
- **계산:** `COUNT(DISTINCT user_pseudo_id)` from `ops_f_sessions` where `session_date = D`
- **7일·월 누적:** **사용자-일 합계** (DAU의 합). 고유 사용자 수(WAU, MAU)가 아니다
- **한계:** `user_pseudo_id`는 브라우저·기기 단위 익명 ID라서, 한 사람이 기기를 바꾸거나 쿠키를 지우면 다른 사용자로 잡힌다
- **표기:** `3,421`
- **SQL:** `03_ops_kpi_daily.sql` (`active_users`)

### K05_session_cvr · 세션 전환율

- **정의:** 그날 세션 중 주문이 1건 이상 생긴 세션의 비율
- **분자:** 중복 제거 후 주문이 1건 이상인 세션-일 수 (`ops_f_sessions.orders > 0`)
- **분모:** 세션-일 수 (K03)
- **7일·월 누적:** 분자 합 / 분모 합
- **표기:** `1.56%`, 증감은 `%p`
- **한계:** 원본 purchase 이벤트가 있는 세션 수와 조금 다르다. 다른 세션에서 재전송된 주문은 첫 세션에만 남기 때문이다 (R3)
- **SQL:** `03_ops_kpi_daily.sql` (`order_sessions / sessions`), `04_ops_kpi_comparison.sql`

### K06_aov · 객단가

- **정의:** 매출값이 있는 주문 1건당 평균 금액
- **분자:** K01 매출
- **분모:** 매출값이 있는 주문 수 (`has_revenue = TRUE`)
- **제외:** 매출값이 없는 주문은 분모에서 뺀다. 넣으면 금액 0인 주문처럼 계산돼 객단가가 낮아진다
- **7일·월 누적:** 매출 합 / 매출이 있는 주문 수 합
- **표기:** `$61.46` (소수점 2자리)
- **SQL:** `03_ops_kpi_daily.sql` (`revenue / orders_with_revenue`), `04_ops_kpi_comparison.sql`

**매출 분해 관계 (일 단위 설명용)**

```text
매출 ≈ 세션 × 세션 전환율 × (주문 수 / 주문 세션 수) × 객단가
```

한 세션에 주문이 여러 건인 경우가 있어 "주문 세션당 주문 수" 항이 들어간다. 대부분 1에 가까우므로 리포트에서는 `세션 × 전환율 × 객단가`로 설명하고, 이 항은 참고값으로 둔다.

flag 임계치는 EDA의 92일 변동성 분포에서 잡은 v1.0 초안이다 (01 문서 2-3장).

| metric_id | 지표 | 계산식 | Grain | 용도 |
|---|---|---|---|---|
| D01_view_item_rate | 상품 조회율 | view_item 세션 / 세션 | 세션 | 퍼널 1단계 |

### 4-1. 퍼널 정의

```text
세션 → 상품 조회 (view_item) → 체크아웃 (begin_checkout) → 구매 (중복 제거 후 주문이 있는 세션)
```

- **단위:** 세션-일. 각 단계는 그 세션-일에 해당 이벤트가 1건 이상 있었는지(도달 여부)로 센다. 이벤트 횟수가 아니다.
- **순서는 보지 않는다.** 단계 간 역전이 거의 없어서 도달 기준으로 충분하다 (12월: 체크아웃 없이 구매 1세션, 상품 조회 없이 구매 81세션 = 구매의 4%, `sql/eda/11`).
- **장바구니는 퍼널 단계가 아니다.** 12월 체크아웃 세션의 23%(987세션)는 같은 세션에 장바구니가 없었고, 그중 79%는 그 전에도 장바구니를 쓴 적이 없는 사용자였다 (바로 구매, `sql/eda/12`). 장바구니를 단계로 넣으면 "장바구니 → 체크아웃" 비율이 100%를 넘거나, 구매자의 상당수가 퍼널에서 빠진다. 그래서 장바구니율(D02)은 참고 지표로 따로 본다.
- 비율 지표는 %p 차이로 비교한다.

## 6. 집계 대사 규칙 (집계 전에 매일 실행)

같은 숫자를 서로 다른 단위로 계산해서 맞아떨어지는지 확인한다. 하나라도 실패하면 그날 리포트에 "해석 보류"를 붙인다.

| rule_id | 대사 | 통과 조건 | 92일 검증 결과 (`09_order_reconciliation.sql`) |
|---|---|---|---|
| R1 | 이벤트 → 주문 | 주문 수 ≤ purchase 이벤트 수 | 5,283 ≤ 5,692 ✓ |
| R2 | 주문 매출 = 세션 합산 매출 | 차이 0 | 338,153 = 338,153 ✓ |
| R3 | 주문 세션 수 vs 원본 purchase 세션 수 | 차이가 "세션을 넘는 중복 거래번호" 수 이하 | 4,837 vs 4,848, 차이 11 ≤ 15 ✓ |
| R4 | 주문 수 = 거래번호 있는 주문 + 없는 주문 | 차이 0 | 4,451 + 832 = 5,283 ✓ |
| R5 | 중복 제거 매출 ≤ 원본 매출 | 항상 성립 | 338,153 ≤ 362,165 ✓ (−6.6%) |
| R6 | 일별 합계 = 기간 합계 | 일별 K01·K02 합이 기간 집계와 일치 | 파이프라인 구축 시 추가 |
